# Workload and isolated verification runner

This directory implements the resettable generated-code verification workload for the exploratory application pilot. It contains 656 selected published Llama-3.1-8B candidate records across all 164 HumanEval tasks. Eighty candidates on 20 tasks form an engineering development partition; 576 candidates on 144 tasks form 18 evaluation batches of eight tasks each. All 164 tasks were previously exposed in earlier local work. This split is not an unseen-task or contamination-free holdout, and no new model generations are claimed.

## Inputs, selection and rights

`manifest.json` records source hashes, official source URLs, execution hashes and pre-freeze revisions. `catalog.json` embeds every selected program and unchanged official test string. `batches.json` preserves task ordering and source indices without program text.

The published candidate input is the verified 73,874,142-byte JSON member with SHA256 `4ef4b6b65e77ba2b1f44b6f890ac5d1f7e82b817bbdb7492b71fa1f825ef3522`. The catalog field `source_archive_sha256` refers to this uncompressed JSON member, not the entire enclosing ZIP. `sources/candidate_download_recipe.json` provides the pinned author README, exact public ZIP/member and reconstruction steps. No license covering these candidate programs was established. The future public S9 bundle excludes the full raw archive, selected candidate code, catalog solutions, input payloads and any source-bearing logs; it supplies official tests, code-free metadata/results and the download/extraction recipe. The local author bundle may retain inputs. The MIT label below applies to official HumanEval materials, not the candidate archive. No model-weight byte identity is claimed.

The archive is linked by the author repository for Benedikt Stroebl, Sayash Kapoor and Arvind Narayanan, *The Limits of Inference Scaling Through Resampling*, arXiv:2411.17501v3 (26 March 2026), DOI `10.48550/arXiv.2411.17501`. The pinned author README at commit `11a8f6ed1aee5b996f659c3fedb549c07aeb34ad` identifies the sanitized HumanEval samples and sample-collection implementation. The public download is `https://www.dropbox.com/scl/fi/je3d9lrmu36g5x3alugsa/humaneval_evalplus.zip?rlkey=del4cd36kfyyseaw7r9zs8gn0&dl=1`; the exact member is `humaneval/meta-llama--Meta-Llama-3.1-8B-Instruct_openai_temp_0.8-sanitized/eval_results.json`. These metadata were verified against the [pinned author README](https://raw.githubusercontent.com/benediktstroebl/inference-scaling-limits/11a8f6ed1aee5b996f659c3fedb549c07aeb34ad/README.md) and [arXiv primary record](https://arxiv.org/abs/2411.17501v3) on 12 September 2026. They establish the published artifact's origin, not a reconstruction of every generation setting or historical test outcome.

Official HumanEval data and its MIT license were fetched from `openai/human-eval` commit `6d43fb980f9fee3c892a914eda09951f772ad10d`. `sources/HumanEval.jsonl.gz` contains all 164 tasks and has SHA256 `b796127e635a67f93fb35c04f4cb03cf06f38c8072ee7cee8833d7bee06979ef`. `sources/HUMANEVAL_LICENSE` has SHA256 `bcba3de214851cce46ed5af42d6698044616eeace887c3231bc7a20474ab639e`. This workload does not use CodeT-generated tests or their labels as the correctness oracle.

For each task, `prepare_workload.py` takes the first four source array indices after ascending SHA256 order of UTF-8 `iasc-app-20260912-v1|{task_id}|{source_array_index}`. Tasks are independently sorted by SHA256 of UTF-8 `iasc-app-task-order-v1|{task_id}`; the first 20 are development. The builder parses the archive but accesses only task-map keys, source array indices and `solution` strings. It does not read archived pass/fail labels. It preserves 10 empty selected programs and six within-task duplicate selections. The rank is this hash rank, not a claim about original model generation order. Program and test hashes cover their exact UTF-8 strings without normalization.

## API and execution semantics

```python
from pathlib import Path
from job_runner import run_job
result = run_job(job_dict, Path("fresh_empty_operation_directory"))
```

`job_dict` is one complete embedded catalog job. All sandbox paths are resolved relative to `job_runner.py`; catalog location need not be supplied. The output directory must be empty. The runner verifies the program/test hashes and execution bundle before launching. It never imports or executes a candidate in the Windows host process. Windows launches use `CREATE_NO_WINDOW`.

Each call starts a fresh WSL/bubblewrap namespace and then a fresh child for one official suite. The parent records `suite_started` with child PID, task, candidate and job digest before releasing the child through a pipe handshake. The child runs the selected complete program, loads the unchanged official suite in a separate dictionary inheriting program globals, and invokes its `check` on the entry point. The inherited helper names are required by official tests for HumanEval/32, /33, /38 and /50. This establishes functional-suite outcomes for the published samples; it is not a claim of resistance to deliberately harness-aware malicious Python.

The suite parent enforces a 3.0-second wall timeout, kills the child on expiry and obtains child user-plus-system CPU time from `wait4`. The copied launcher applies a 512 MiB address-space limit, 10-second CPU soft limit, 15-second outer wall limit and a two-second kill grace. Address-space limits are not cgroup RSS limits. The namespace uses uid/gid 65534, no network, dropped capabilities, a 32 MiB temporary filesystem, read-only inputs/runtime, and a strict child seccomp filter denying process creation, OS exec and network syscalls. Host output files are not mounted into the sandbox. The existing launcher/bootstrap/guard were copied from the local v3 follow-up runner; the suite worker is new.

The installed WSL Ubuntu-24.04 runtime and packages are dependencies, not fully covered by the five-file runner bundle. The copied launcher checks the existing bubblewrap binary SHA256 `52231e1caf55bcbc667b269f49c63599a6f7db4767ae6a039580d0ff853db712` before use and enumerates allowed scientific/pytest package paths. It is currently configured for this workspace and installed WSL environment. The bundle is not a portable container image or whole-runtime attestation.

Results have `status` equal to `pass`, `fail`, `timeout` or `infrastructure_error`; ordinary completed jobs have `actual_starts=1` and `actual_start_known=true`. An infrastructure failure after a host launch with no trusted child-start event has unknown start state. A rejected prelaunch has known zero starts. Infrastructure outcomes must not be silently counted as suite failures or as proof that no process started.

`wall_seconds` measures parent-supervised suite duration. `cpu_seconds` is child CPU from `wait4`. `launcher_wall_seconds` includes WSL/namespace startup and collection. Windows `host_launch_perf_counter_ns` is sampled immediately before `Popen`; `host_exit_perf_counter_ns` is sampled after the host launcher joins. These host timestamps are comparable to the service/workflow clock, but the launch boundary identifies the WSL/bash launcher; the separately recorded `suite_started` identifies the candidate child. These measures support a count of actual starts and observed timing, not a claim that the decision budget enforces aggregate CPU seconds.

Artifacts include invocation and host-launch receipts, trusted start events, launcher/supervisor logs, and `result.json`. Candidate stdout and stderr are separately captured and bounded to 64 KiB per returned channel; their contents are never parsed as start or pass receipts. The parent reports byte lengths and truncation flags.

The top-level `runner_manifest` maps the five execution files to SHA256. `runner_sha256` hashes the compact, sorted, UTF-8 JSON of that manifest (`ensure_ascii=False`). Job identity hashes the same canonical JSON encoding of exactly `task_id`, `candidate_id`, `solution_sha256`, `test_sha256`, and `runner_sha256`. This identity supports the service's `verify:<digest>` decision ID and `job:<digest>` evidence ID.

## QA and preservation

`run_qa.py` permits only harmless selftests, canonical reference solutions or the 80 development candidates. It has no evaluation-candidate mode. Reference solutions are official `prompt + canonical_solution`; running their 164 suites is runner QA, not execution of the selected evaluation candidates. Each QA directory preserves individual inputs, receipts, results, aggregate results and a summary.

Initial reference QA passed 160/164 and exposed missing program-global helper names in a fully empty test namespace. That version and its outputs are retained in `qa_revision_v1/` and `qa_reference_v1/`. The corrected inherited-global namespace passed all 164 suites. A second pre-freeze correction made missing-start state unknown after a launched host process, including outer-controller timeout; previous files and QA are retained in `qa_revision_v2/`. Synthetic branch QA records its mocked PID explicitly and is excluded from actual-launch evidence. `RUNTIME_FEASIBILITY.json` identifies the final QA, timing calibration and exact final hashes.

The catalog builder's `candidate_execution_performed=false` records the builder action only; subsequent development execution is documented by the QA directories. No evaluation candidate was executed by this workload implementation subtask before protocol freeze. Formal evaluation remains the parent workflow's separately authorized operation.
