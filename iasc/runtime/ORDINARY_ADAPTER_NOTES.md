# Independent ordinary transaction/idempotency adapter

Implementation: `ordinary_adapter.py`. SHA-256: `f212202223d8a6217306ef240d864ccf10aa80889043f21cb9e60c5e03dff634`. This final version adds `jobs` and standardized `capacity_rows` to the read-only `snapshot()` interface without changing delivery behavior. After that interface addition, all 19 checks passed again in `ordinary_unit_checks_v3/`, and the actual-service smoke passed again in `ordinary_http_smoke_v3/`; use these final-version artifacts for packaging. The v2 checks described below retain the pre-interface-change history.

The adapter implements the shared `PROTOCOL.md` delivery boundary using only Python's standard library and a separately designed SQLite schema (`policy`, `permit_registry`, `budgets`, `holds`, `delivery`, `receipts`). It imports no ECRC types, validation, ledger, fixture generators, canonical helpers, the ECRC HTTP adapter, or its recovery logic. It does not make HTTP calls. The harness supplies the same preissued fixture and the same service/transport behavior to both arms. Original ECRC adjudication produced that trusted fixture before delivery timing; this is not an independently implemented issuance comparison or a blinded clean-room study.

`seed` checks the complete supplied permit inventory against trusted registered content hashes and binding fields, imports the policy and reservation/capacity state, and verifies per-scope held/spent accounting. It rejects a conflicting replacement fixture. New `arm` calls validate exact trusted content, active policy, the permit interval at the supplied authorization clock, an authorized action route, finite claim/evidence relations, and the corresponding held reservation/capacity binding in the same `BEGIN IMMEDIATE` transaction that persists the immutable intent. The payload is exactly the protocol's four permitted fields. The logical key is the permit ID.

Once armed, the matching grant can be retrieved after expiry or revocation. Changed content under the same key is rejected. `finish` validates key/hash/effect identity, acknowledged payload content, and the service timestamp; it commits the held capacity, inserts one receipt, and marks the intent receipted in one local transaction. Its optional `before_commit` callback runs after all SQL writes but before commit, enabling the shared harness to kill the worker in that precise transaction window. Matching repeated completion returns the existing receipt. An uncertain intent remains armed and its capacity remains held; there is no timeout-driven release or cancellation path.

The actual positive integer service `effect_id` is retained as `service_effect_id`/`effect_id` and in the original ACK; `side_effect_id` is its string representation for comparison convenience. The receipt separates:

- `armed_at`: supplied authorization-policy clock used to establish the grant;
- `committed_at` / `executed_at`: actual service-record timestamp from the ACK;
- `reconciled_at`: actual local UTC clock read when recording the completion;
- `reconciliation_policy_clock`: the supplied completion-policy clock, including explicit logical-clock boundary injection.

No physical effect timestamp is moved back into an expired permit interval. This is the new irrevocable-grant contract, not an assertion that the original `StatefulReceiptVerifier` accepts these boundary cases unchanged.

## Checks completed before the shared benchmark

`test_ordinary_adapter.py --out ordinary_unit_checks_v2` passed 19/19 API checks. These use independently hand-authored ordinary-record fixtures, plus one compatibility check using `smoke_fixture2/fixture.json` produced by actual original ECRC adjudication. All ACKs in these unit checks are explicitly synthetic, with the service's positive-integer ID schema. Coverage includes valid/repeated completion; changed registered claims; expiry/revocation before arm; nonaction rejection; irrevocable grants after expiry/revocation; transaction exception rollback; changed content under an armed key; mismatched ACK key/hash/payload or missing effect ID; reservation binding conflict; inconsistent imported budget accounting; eight concurrent threads; reopening a durable intent; and unarmed completion rejection. These checks do not enter the benchmark's prespecified crash-scenario denominator.

`smoke_ordinary_http.py` additionally passed a real HTTP compatibility check against the actual `service.py` in its own process and database. The first POST returned 201; the retry returned 200 with the same durable effect; the independently queried sink held exactly one effect, and the ordinary client held one receipt, one committed unit and zero reserved units. Its receipt effect ID/hash/commit timestamp matched the independent sink row. This is a compatibility smoke check, not a crash-recovery experiment or a workload repetition. Results and databases are retained in `ordinary_http_smoke/`.

`ordinary_unit_checks/` contains the earlier API-check run made before the service's integer-ID schema was finalized. It is historical and is superseded by `ordinary_unit_checks_v2/`; do not cite the earlier string-ID synthetic ACKs as current compatibility evidence. The adapter was then tested against the actual HTTP schema without further algorithm changes.

The common harness supplies the planned process-kill, lost-response, service-restart, outage, concurrency and timing experiments. Their observed results remain separate from these implementation checks. The adapter itself does not establish that a physical effect occurred; the harness must inspect the independent sink database and reconcile it with the client state. Trust in the local host, service, policy and issuance registry remains an assumption.
