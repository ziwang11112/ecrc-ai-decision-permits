# ECRC runtime boundary and a minimal independent-service extension

Read-only implementation review, 2026-09-11. No original runtime, manuscript, or archived experiment was changed. The review covers the current governance package and the official-v2 runtime bridge. This document is a design review, not an execution result or a claim that the proposed extension already works.

**Subsequent protocol decision.** `PROTOCOL.md` now fixes the authorization boundary at a committed durable intent: an armed grant is irrevocable, and later expiry/revocation blocks new intents but not recovery of this operation. The new adapter therefore needs its own delivery-receipt checks; the original verifier's effect-before-permit-expiry requirement is not an acceptance criterion for the new logical-clock expiry boundary. Record `armed_at`, the service's real `committed_at`, real local `reconciled_at`, and the injected `reconciliation_policy_clock` separately. The service's effect ID is a positive SQLite integer, preserved in the extended receipt/ACK (the original ECRC typed `side_effect_id` field may contain its string representation). Original adjudication constructs and persists the shared fixture before measured dispatch; independent issuance/crashes in the earlier issuance gap are outside this comparison.

## Finding and feasible adapter

The existing ECRC runtime can supply real policy/evidence adjudication, trusted permit issuance, capacity reservations, typed permits, canonical hashes, and receipt-chain verification. Its execution path is explicitly a **SQLite simulator**. It has no HTTP effect callback and cannot make a transaction atomic with another process or database. A local HTTP service with its own durable database therefore requires a new transport/outbox adapter and service-side idempotency; merely sending HTTP before or after `PEPSimulator.execute` would leave an unhandled crash window.

The smallest credible extension keeps the original governance code unchanged, adds an adapter-owned outbox table to the same client ledger database, and uses a separately running loopback HTTP service with its own SQLite database. The service performs a simple durable synthetic effect (for example inserting a dispatch record) and stores its idempotency acknowledgement in one service transaction. The client submits a stable logical-operation key and payload hash, retries the same request after uncertain outcomes, and records the service's acknowledged effect in a later local transaction. This is two local transactions connected by recovery, not a distributed atomic transaction.

## What remains only a simulator

`PEPSimulator` states this limitation directly (`enforcement.py:11–16`). Its `execute()` first invokes `validate()` and then calls `SQLiteCapacityLedger.complete_execution()` (`enforcement.py:78–101`). It has no service URL, network transport, effect callback, or independently observed acknowledgement.

Inside `complete_execution()` (`ledger.py:847–992`), one local `BEGIN IMMEDIATE` checks active policy and registered permit, rejects a consumed permit, commits/releases capacity, constructs a deterministic `effect_*` identifier with `stable_id`, appends an `ExecutionReceipt`, inserts an execution row, and commits. No external action is performed. The identifier at `ledger.py:905` is generated from permit identity/hash and enforcement-point identity, rather than returned by an external effect service. Directly calling this function after an HTTP acknowledgement would still invent its own effect identifier and conflate two different operations.

`run_official_v2_runtime_bridge.py:195` builds a policy for the frozen HGB bridge, and `proposal_and_evidence():236` builds envelopes from frozen participant/trial scores and source hashes. The loop at lines 377–383 calls the adjudicator and `pep.execute`. Output explicitly records `simulated_side_effect=True` (line 412), `side_effect_mode="SQLite PEP simulation only"` (line 559), and `live_deployment=False`. Its fixed January 2026 timestamps are replay timestamps; use real current timestamps for a new service experiment, or explicitly separate a logical authorization clock from physical event timestamps. Do not relabel the original bridge as a real-service experiment.

## Permit and HTTP payload construction

For a small systems experiment, use a new deterministic **synthetic** policy/proposal/evidence fixture, rather than importing the entire behavioral replay script and its pandas/model dependencies. Reuse the same public dataclasses and adjudicator as the bridge. Register an approved synthetic model hash and a synthetic evidence rule, define alert/review plus nonaction claims, and set a prespecified small capacity. Timestamps should be generated from a saved run origin, and test expiry/revocation intentionally rather than relying on a January replay clock. The test fixture must be identified as synthetic systems input, not new behavioral evidence.

For each input, call `adjudicate`, retain `permit.to_dict()` or its exact canonical JSON and its hash, and preserve the proposal/evidence inputs used to produce it. The approved HTTP body should be a deterministic projection of permitted fields, e.g. logical operation ID, route, permitted finite claims, evidence hash and permit/content binding. A generic arbitrary text/body supplied after issuance is **not** bound merely because a permit ID accompanies it. Either derive the whole effect body from the registered permit/fixture, or explicitly add a trusted effect-payload hash at authorization and verify it before dispatch.

Use a stable key for the logical operation, independent of retry number, PID, wall time, recovery attempt or generated receipt ID. Separate arms/runs with separate service databases or an explicit namespace so one arm does not inherit another arm's idempotency result. The service key-to-payload mapping must be immutable: same key plus same body returns the original acknowledgement; same key plus different body returns an explicit conflict and performs no new effect.

## Recommended state and transaction boundaries

Add an adapter-owned table to the ECRC client database, for example:

```text
dispatch_outbox(
  operation_id PRIMARY KEY,
  permit_id UNIQUE, permit_hash, permit_json,
  request_hash, request_json,
  state, authorised_at, attempted_at, attempt_count,
  service_effect_id, service_effect_at, service_ack_json,
  completed_at, receipt_id
)
```

Names are suggestions; the common protocol should fix the external API and observed state invariants before either implementation runs. A conventional baseline can use different internal tables with the same capabilities and contract.

1. **Authorize and persist intent, local transaction A.** Recheck registered permit, active policy, route, permit time bounds, and reservation binding inside the same `BEGIN IMMEDIATE` that inserts a unique immutable outbox intent. On an existing key, compare both content hashes and return its prior state; do not reset completed work. Public `PEPSimulator.validate()` can be a preliminary convenience check but is not a substitute for transaction-local checks. Read the current validity time while establishing this authorization boundary. `complete_execution()` itself does not repeat all permit-time checks performed by `PEPSimulator.validate()`, so bypassing the latter requires explicit checks in the adapter.
2. **Dispatch outside transaction A.** Commit the intent before making the HTTP request. Marking a row attempting/uncertain is useful for audit; correctness must tolerate the client dying before/after that marker. Do not hold a SQLite write transaction over the HTTP request, and do not treat a timeout as a definitive failure.
3. **Perform and acknowledge the service effect, independent service transaction B.** `POST /effects` receives key and immutable request. In a service `BEGIN IMMEDIATE`, inspect the unique key; reject a body-hash conflict, or return the original acknowledgement, or atomically insert the effect plus key/body hash/acknowledgement and commit. The HTTP response occurs after that commit. A read-only status endpoint can return the same durable acknowledgement. No client database transaction participates in B.
4. **Reconcile acknowledgement, local transaction C.** Validate that the acknowledgement binds the operation key, request hash, effect ID and service effect time. Recheck the trusted permit identity, commit the corresponding reservation using the connection-level helper, construct a receipt with the **service's** effect ID/time, append its chain link and execution row, and mark the outbox done in one client transaction. A repeated completion must return the already-stored receipt if the content matches. Store `completed_at` separately from effect time so recovery never conceals a delay by backdating completion.
5. **Recover.** Enumerate unresolved durable intents and replay the same key/request or query its acknowledgement, then run the same idempotent completion. A crash after B but before C must result in one durable service effect and eventually one local completion; a crash after C must not create another local receipt or capacity commit. Duplicate workers may create multiple attempts; service uniqueness plus serialized local completion should still prevent duplicate effects/completions.
6. **Nonaction route.** Record a local `not_executed` receipt without submitting a POST. An unknown/rejected policy, altered unregistered permit, invalid claim/body, or exhausted capacity must not create an effect. Keep a terminal refusal distinct from an uncertain already-authorized dispatch.

There is intentionally no cross-database atomicity claim. During recovery, an effect may be durable while the client remains uncertain and its capacity remains reserved. Measure that state and its eventual resolution instead of calling it a contradiction or hiding it from totals.

## Two boundaries the protocol must state explicitly

**Issuance-to-outbox crash gap.** The adjudicator reserves capacity and registers issuance in separate original transactions, before adapter transaction A. The issued-permit registry stores hashes and binding fields, not a complete permit document. `reap_expired_reservations()` only releases **unissued** reservations (`ledger.py:636–680`); it deliberately excludes issued reservations. Therefore it cannot automatically repair a crash after issuance but before an outbox document exists. The minimal experiment can prespecify that fault injection starts after full permit/intent input persistence and report this scope. To cover the earlier gap, persist recoverable request/envelope data before adjudication and resume issuance deterministically; for nonaction permits, changing the issuance timestamp on replay changes the payload, so a saved authorization time is necessary. Merely scanning `issued_permits` is insufficient to reconstruct full claim/evidence fields.

**Expiry, revocation and uncertain outcomes.** Fix a policy for new dispatch authorization versus reconciliation of an effect already committed by the service. Do not reject or erase an existing durable effect solely because recovery occurs after expiry/revocation, and do not resend a new effect after expiry under a fresh key. An existing service acknowledgement can be reconciled using its actual effect time; a recovered receipt's `executed_at` should denote that time, with separate later `completed_at`. If the service has no record and creation might still be possible, a timeout/absence observation alone is not a safe cancellation fence. The smallest crash benchmark may use a validity window covering every retry and declare dynamic revocation/expiry during in-flight delivery out of scope. Testing that boundary requires a service-enforced deadline or terminal cancellation/tombstone contract, shared by both arms; do not infer it from client checks alone.

## Fair conventional baseline and common harness

The second arm should be a separately implemented ordinary JSON/SQLite transaction-and-idempotency adapter. It should receive the same authorized fixture content, trust metadata, durable intent capability, capacity budget, service endpoints, key/body conflict handling, retry opportunities, and fault schedule. It must not call ECRC adjudication/validation/ledger functions to implement its checks or reuse the ECRC adapter's outbox/recovery helpers. Shared HTTP transport or service code is acceptable if fixed by the common protocol and disclosed; separate client control logic and database schemas are preferable. Its content checks should not be intentionally weakened. Ties are a valid outcome and would attribute recovery to transactional outbox/idempotency capabilities rather than specialized record names.

The common harness should launch the service and client as separate OS processes and retain separate client/service database files. A committed row in the service database is a real persistent synthetic effect across processes, but still not delivery of a real clinical alert or any intervention benefit. Use prespecified process termination points around: intent commit; before service commit; after service commit/before response; response received/before client completion; during local completion before commit; and after local completion before return. Distinguish client crashes from service crashes and use a persisted one-shot trigger so a restarted process does not endlessly repeat the same injected crash.

At each injected point and after recovery, the harness—not either adapter's self-report—should independently count physical service effects per logical operation, payload conflicts, valid/invalid authorization, outstanding intent state, reservation/committed capacity, local receipt uniqueness, and agreement of receipt effect IDs/hashes with the independent service record. Persist process exit codes and fault markers to establish that a real failure occurred. A normal run, repeated valid call, conflicting-key call, invalid permit, nonaction route, and independent manually constructed edge cases provide controls. A service acknowledgement is not an independent scientific outcome; it is the witness for this restricted systems effect.

## Claims the extension could and could not support

If successful, it can support recovery of a specified synthetic durable HTTP effect across prespecified single-client/single-service crash windows, with observed duplicate-effect and unresolved-operation counts and a fair conventional comparator. It can show that an adapter is more than the original SQLite-only simulator.

It would not prove distributed exactly-once execution in general, unlimited fault coverage, tolerance of a compromised service/ledger, immediate global revocation, exactly-once messaging over arbitrary APIs, power-loss durability without testing storage assumptions, multi-host consensus, clinical effectiveness, or superiority over a conventional implementation with the same capabilities. Local HTTP plus a separate process/database is a real process/service boundary; it is not evidence of internet/network-partition behavior or a production deployment. Explicitly record SQLite journal/synchronous settings in the new experiment rather than assuming crash and power-loss guarantees are interchangeable.
