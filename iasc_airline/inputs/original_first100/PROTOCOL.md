# Fixed native-record coverage validation

This study is declared before any comparison on the generated requests. A review
found that all original airline test tasks had already been source-screened and
that several of their initial cancellation clauses reuse development accounts or
reservations. That split cannot supply an unseen confirmation claim. Its six
initial-cancellation requests are retained separately as an exposed extension.

This study instead asks whether the unchanged qualification-to-permission
connection both admits eligible actions and avoids ineligible or insufficiently
specified actions across a larger fixed set of native records. These are scripted
requests constructed over the pinned tau2 native database, NOT additional official
benchmark tasks, real customer conversations, or a new independent dataset.

## Cohort and fixed interventions

The native source contains 500 users and 2,000 reservations. Exclude accounts
explicitly present in all 50 official public user scenarios and accounts queried
by the recorded earlier airline development actors. The exclusion manifest keeps
the exact prior log files and account IDs; future logs do not change this cohort.
Prior global database access cannot be excluded, so no never-seen claim is made.

Use only valid user/reservation ownership linkage to form the eligible sampling
universe. Do not select using cabin, insurance, age, status, qualification, gold
actions, or execution outcomes. The seed `ecrc-native-record-coverage-v1` fixes
hash order. Select the first 100 distinct accounts, or all if fewer exist, and
one owned reservation per account by the declared hash order. Keep the exact
formula and source hashes in COHORT_SELECTION.json. The 100-account limit is a
fixed resource scope, not a power calculation or a guarantee of enough positives.

For every selected reservation, construct exactly three requests: health (the
scripted user reports sickness), other (the scripted user reports booking by
mistake), and unspecified (the scripted user supplies no cancellation reason).
All request identities are frozen before native execution. Each asks to cancel
that one reservation; the same full action confirmation is scripted for all arms.
No missing reason is filled during execution. Different reason settings on one
account are paired controlled contexts, not independent people or naturally
observed task frequencies. Do not add records or change templates after results.

## Fixed conditions

For each request run, in rotating order, four conditions from the previous
ablation study: direct_native_dispatch, qualification_ecrc, existing_rules_only,
without_claim_evidence_requirement. The shared resolver, actor workflows, domain
checker, ScopeGate, ablation gate and independent business evaluator are imported
unchanged. The only ablation removes the positive cancellation evidence type from
the permission dependency, not the domain calculation. No models are invoked.

The previous clean-metadata ablation is not repeated: these inputs introduce no
metadata faults and this study does not estimate that component's benefit.
Capacity remains 100 and is nonbinding for the one-reservation cases. There is no
native atomic completion receipt or recovery trial; no finish is manufactured.
Claims concern this qualification/permission integration, not all ECRC components.

## Execution and outcomes

Each cell starts with a fresh original native environment and independent
permission database. Execute actual native calls and retain their chronological
transcript, full confirmations, response bodies, candidate evidence, full final
database and permission state. A shared immutable BEFORE_DB and gzip-compressed
complete AFTER_DB files reduce duplicate storage; per-cell before hashes verify
the shared initial state. Replay every recorded native call on another fresh
environment and check response identity/content and final state. Replay is
validation work, not additional primary samples.

There is no original benchmark task ID for these requests and no official
DB/COMMUNICATE task score. Do not map them to convenient old tasks or invent a
benchmark success rate. The unchanged independent business evaluator receives
the original request, full transcript, and before/after snapshots. A separate
postrun auditor reconstructs actual effects and permission state from raw files.

Report eligible completed/missed, known-ineligible executed, information-missing
or transfer-required candidates and their executions, unresolved selection,
out-of-selection/duplicate effects, confirmations and technical failures. A
flown record requiring transfer stays unresolved/transfer, not a successful
completed refusal. An eligible action means cancellation under this controlled
native policy; suite/task validity does not imply money saved or customer benefit.

Show results by reason setting and pooled as controlled request opportunities,
with the number of unique accounts/reservations explicit. Also distinguish
missing-information and transfer-required outcomes. The frozen request population
is the denominator; technical or unresolved failures may not be dropped. Report
exact observed counts; do not treat the 3x4 repeated cells per account as 12
independent samples or infer a population rate from template frequencies.

## Freeze and stop

Freeze source selection, requests, protocol, runner, all imported prior sources,
native vendor hashes, independent audit dependencies and manuscript hashes after
synthetic QA and before any native comparison. Run the complete grid once.
Technical failures are retained and make the integrity check fail. A correction
requires a documented version and retention of originals, not replacement of
unfavorable cells. Keep ordinary-rule ties and raw eligible completions.

Stop at this fixed grid even if eligible examples are few, no ablation benefit is
observed, or a component rejects valid requests. No model/API expense. No paper,
Overleaf or GitHub edits in this execution task.
