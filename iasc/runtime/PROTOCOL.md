# Independent local service and crash-recovery protocol

Fixed 2026-09-11 before running the comparison. This is a newly implemented, post hoc engineering extension, not evidence that the archived PEPSimulator already supported external effects. Existing behavioral predictions, statistical analyses and the original runtime source remain unchanged. No external messages, paid APIs or real participant interventions are used. Effects are persistent records in a separate local HTTP service process and database.

## Comparison and guarantee boundary

Two implementations: ECRC with a new durable delivery adapter; and an independently coded ordinary JSON/SQLite transactional outbox with the same trusted issued-permit records, policy snapshot, reservations, stable operation keys, payload binding, durable retries and idempotent sink. No semantic capability is deliberately removed from the baseline. Original ECRC adjudication creates a shared fixture before measured delivery; this is not a comparison of independent issuance implementations. The adapter is explicitly new code. Both arms use the same sink implementation and transport runner. Shared fixture/transport code and source-informed independent checking are disclosed.

Operation payload is derived exclusively from the registered permit: decision_id, route, permitted_claim_ids, used_evidence_ids. The sink atomically commits one durable effect per idempotency key together with its key/hash; a different payload under that key is rejected. The sink, issuance registry, policy authority, host and local databases are trusted. No claim is made about arbitrary non-idempotent services, malicious trusted state, network authentication, multi-node consensus or power-loss/storage-corruption resilience.

Authorization is linearized at the local transaction that validates the current policy and permit, checks the held reservation and registers a unique durable delivery intent. Once armed, this is an irrevocable authorization for this operation; expiry or revocation prevents new intents but does not cancel an accepted intent. Recovery resumes the same intent/key/payload. Commit-time remote revocation would need sink participation and is outside this experiment. No HTTP call occurs while holding a local database transaction. A timeout, disconnect or negative lookup does not prove that the remote effect cannot happen: armed reservations remain held during uncertainty and are never released merely on timeout. This trades availability for safety during an indefinite outage; eventual completion requires recovered communication and functioning workers/sink.

States: issued/unarmed -> armed/in doubt -> receipted. An observed sink acknowledgement may be volatile until reconciliation. Receipt insertion, reservation commitment and final outbox state change are atomic in the local database. Each receipt records the actual sink effect identifier and payload-bound acknowledgement. An idempotent recovery returns an existing receipt without consuming capacity again. Unknown outcomes remain armed. Pending-to-cancelled is deliberately unsupported after authorization; before-arm invalid permits cause no HTTP dispatch.

## Fixed experiments

Five repetitions of each arm for nine recovery scenarios: normal delivery; worker termination after intent commit; worker termination after sink acknowledgement but before local reconciliation; dropped response after sink commit; termination inside the local reconciliation transaction before commit; termination immediately after local reconciliation commit; eight independent workers retrying the same operation; sink termination/restart after lost acknowledgement; and a temporary sink outage followed by recovery. Single-operation cases use capacity one and one preissued action. Parent-controlled checkpoints and explicit process termination exercise deterministic crash windows; these are injected failures, not sampled field incident rates. Store intermediate and final counts for sink effects, local receipts, committed/held units, and final operation state, including the temporarily unresolved outage state. Retain all planned cases.

Additional boundary cases for each arm: changed permit content, expired permit before arm, revoked policy before arm, non-action permit, revocation after arm, and expiry after arm. The last two resume the accepted grant by contract. Service-specific tests separately cover identical-key concurrency, conflicting payload rejection and durable restart. Further cases may be added only as explicitly labelled implementation checks; do not merge them into the predeclared fault denominators.

Expiry boundaries use an injected logical policy clock, not wall-clock waiting. Service commit and local reconciliation timestamps remain actual wall-clock observations and are stored separately from authorization and the injected policy-clock value. Recovery receipts extend the old schema with these delivery fields; original receipt validation requiring execution before permit expiry is not claimed to validate the new durable-grant semantics unchanged.

Failure-free delivery workload: 1, 4 and 8 concurrent worker threads, 64 preissued actions per arm, five repetitions, matched per-scope alert capacity of 64. Start with an untimed operation on a separate scope to warm the service, then time arm-to-receipt wall-clock latency. Alternate arm order by repetition. Report all requests, throughput, median and p95 latency, database size, and observed ranges across runs. The effects cross real local HTTP/independent-process boundaries, but this is a synthetic loopback workload on one Windows host, not a deployment benchmark. Do not attach bootstrap confidence intervals to five dependent system runs or claim statistical equivalence from zero observed failures.

## Validation and artifacts

Before each injected crash, synchronize at a concrete durable or transaction checkpoint. Parent kills a subprocess and verifies its exit before recovery; no blanket sleep stands in for a crash. Query the sink's separate durable database and each local registry independently. Safety checks: no unarmed/rejected operation has an effect; no logical operation has more than one sink effect; reserved plus committed never exceeds configured capacity at observed checkpoints; reconciled receipts match actual sink IDs/hash; no final held units for completed operations; during outage the unresolved unit stays held. Report observation limits rather than claiming an exhaustive proof.

Run the full suite again in a separate output directory with fresh databases and processes. Compare deterministic count/status outcomes; wall-clock times, process IDs, ports, timestamps and raw database bytes are expected to vary. Record actual timing distributions without normalization to force a match. Preserve source snapshots, code and input hashes, complete result CSV/JSON, request/receipt traces, environment, commands and a portable reproduction entry point. All manuscript changes follow the observed results, including equality or failures.
