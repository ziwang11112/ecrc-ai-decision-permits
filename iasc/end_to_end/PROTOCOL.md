# Locked protocol: raw request to independent durable HTTP effect

Design fixed before implementation and experimental execution on 2026-09-11/12. This is a new, post hoc implementation study. It does not retrospectively expand the transaction boundaries or claims of the frozen original ECRC runtime or S6 experiment. New artifacts remain in this directory. Existing predictions, original runtime code and suite results remain unchanged.

## Scope and implementations

Both arms receive byte-identical full policy, proposal and evidence request JSON. The request is durably journaled before issuance. The ECRC arm reuses the frozen original model/adjudicator/ledger semantics through a NEW transaction adapter: reserve, possible release/fallback, issuance registration and full permit journal write share one outer SQLite issuance transaction. Original internal transaction boundaries are suppressed only while this new outer issuance transaction is active. A kill before its commit rolls back all issuance changes, while the previously committed raw request remains available. This atomic issuance wrapper is new functionality, not a claim about the archived adjudicator used on its own.

The ordinary arm independently implements JSON/relational issuance from raw inputs, including policy/input checks, evidence eligibility, routing, reservation, finite claim support, unsupported-action release/fallback, trusted registration and complete permit persistence. It imports no ECRC validation or issuance functions. It can reuse the separately coded ordinary S6 delivery adapter from a copied source snapshot. The implementations may differ in record layout, identifiers and hash formatting. Their common protocol and source-informed development are disclosed; this is not blinded independent rediscovery. Sharing input construction, transport, idempotent sink and harness does not constitute sharing issuance algorithms.

After issuance, both use an arm transaction, a real loopback HTTP request to a separate service process/database, and local acknowledgement reconciliation. The shared frozen sink stores a synthetic record and its dedup key atomically. The key is the resulting permit ID; payload contains decision_id, route, permitted_claim_ids and used_evidence_ids. No actual participant notification or intervention is performed.

## Fixed authorization and cleanup semantics

One policy revision, one subject/session scope, alert budget K=2 and review budget K=1. These are cumulative budgets, not recyclable concurrency slots. Policy timestamps are injected for deterministic boundaries; sink and local receipt times remain actual wall-clock observations. Permit TTL is 3,600 policy-clock seconds; pending raw-request cleanup lease is 60 seconds. Policy validity covers every injected clock used here.

Before issuance commits, reservations are uncommitted. A terminated issuance transaction must leave no registered permit, capacity change or partial permit journal. Retrying re-reads the original durable raw request; the parent must not supply a preissued permit from memory.

After issuance commit and before arm, the full permit remains durable. Ordinary cleanup before permit expiry must leave it available for recovery. At/after expiry, cleanup may atomically cancel a still-unarmed request and release its held reservation; the cancelled request cannot subsequently arm or dispatch. The raw request/issued record remains for audit. An issued non-action outcome is terminal and dispatches nothing.

An existing armed intent is an irrevocable grant. Cleanup never releases it merely because permit time has elapsed, a response is lost, or the outcome is unknown. An unknown effect with held capacity is an allowed recorded intermediate or terminal state. Reconciliation commits held capacity and records the actual sink effect after a matching ACK. Eventual completion requires restored communication and continued recovery. No cancellation after arm, current-action utility guarantee, cross-revision budget guarantee, malicious authority guarantee or power-loss guarantee is claimed.

Unsupported claim support is evaluated after a provisional route reservation, matching the declared ordering. The issuance transaction must retain an audit record of the released reservation, restore that unit for a subsequent supported request and register the allowed non-action fallback. If the process dies before this transaction commits, all of these issuance changes roll back together.

## Fixed case matrix and repetitions

Three repetitions of each of six scenarios for each implementation: 36 primary runs. Run order alternates arm order by repetition. All runs and failures are retained. Distinct requests use different decision IDs and contend on the same finite budget. Concurrent winner identities are allowed to differ; the comparison requires identical inputs, contract-conforming counts, correct per-request bindings and bounded state, not identical winning IDs or sink effect IDs.

1. **distinct_contenders**: eight distinct supported alert requests released concurrently at K=2; then replay every original raw request. Expected two alert effects and six capacity-fallback non-actions, with no duplicate effect or second issuance.
2. **mixed_claim_fallback**: first one high-score request with admitted authorization context but insufficient evidence type for its action claim; require reserve/release/fallback and reusable alert budget. Then four supported alert and four supported review requests compete concurrently, followed by raw-request retries. Expected two alert and one review effects; the unsupported request has no effect and its released reservation is preserved.
3. **kill_during_issuance**: one distinct supported request pauses after provisional reservation SQL, before the outer issuance commit; the parent terminates and verifies exit. Record an independent database snapshot, then recover it from its durable raw request alongside seven other distinct alert requests. Expected no partial issuance after kill and two final effects across eight requests.
4. **kill_after_issue_resume**: one request pauses after atomic issuance/permit-journal commit but before arm; terminate. Run cleanup at a clock before expiry, record its still-held state, then resume it with seven other distinct alert contenders from raw journals. Expected full permit recoverability and two final effects.
5. **expired_unarmed_cleanup**: the first request is killed after issuance commit, remains unarmed, then reaches its exact permit expiry under the injected clock. Cleanup must cancel and release it. Attempt replay of that cancelled raw request and verify no dispatch; run eight new distinct supported contenders against the released budget. Expected two new effects, zero effects for the cancelled request, and an explicit released reservation/cancelled journal.
6. **accepted_timeout_cleanup_recovery**: one request reaches a durable sink effect but the service intentionally drops the response; local receipt is absent. Record the independent sink/client state; invoke cleanup after its permit expiry and verify the armed reservation stays held. Recover from the same raw journal together with seven other distinct alert contenders. Expected two total effects, the original effect reconciled without duplication, and no timeout-triggered release.

The cases are checkpoint-based engineering tests, not random fault sampling. Repetition counts do not estimate field failure rates. If a development or formal run fails, retain its trace and report the failure; fixes require new version hashes and a clear development-versus-formal distinction. No performance inference is planned.

## Inputs, auditing and reproducibility

Save all original request JSON, policy, source snapshots and SHA-256 manifests. Preserve fresh per-run client and sink databases, process logs, crash exit codes, intermediate database backups, final trace and outcome CSV. The independent audit must read raw SQLite tables in read-only mode rather than trust adapter summary counts. Check each capacity row nonnegative and within its own limit, reconstruct reserved/committed totals from reservation rows, verify every effect's permit/key/payload binding and route/claim/evidence membership, and compare local receipt effect IDs/hashes/timestamps with the actual sink rows. Check every cancelled/non-action request has no effect and every completed receipt has a real effect. Issued raw request hashes must match the exact shared input files.

Fairness checks compare whole raw-input canonical hashes between arms. They do not require identical permit identifiers, receipt chains, effect IDs or concurrent winners. Record supplied information, independently implemented functions and all reused components in a capability/source matrix. Retain observed unknown states and do not manufacture missing ACKs. A portable runner takes a new output directory; all references must resolve inside this directory's source snapshots and inputs.

Before formal runs, freeze code hashes after an independent implementation review. The formal report includes all 36 planned rows even if a row fails. Any additional checks are labelled QA and kept outside that denominator. No original manuscript edit is performed by this experiment subtask; report exact English methods/results snippets and limits to the parent.
