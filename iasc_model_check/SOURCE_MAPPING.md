# Source-to-abstraction review for the bounded S8 lifecycle model

This document maps the proposed abstract transitions to the complete frozen S8 implementations. It is an internal, source-based review, not a machine-checked refinement proof. No model or application execution was performed for this mapping. The separate static review of the actual model and configurations is recorded in `MODEL_REVIEW.json`; it is not a model-checking result. `CHECKPOINT_PREFIX_MAPPING.md` records a limited correspondence check against earlier immutable S8 records.

## Scope and source identity

The modeled scope is one fixed policy identifier, policy revision, scope and action route, with a cumulative budget charged one unit per admitted action. The two declared finite instances contain two request identities with capacity one and three request identities with capacity two. Legal proposal/evidence content, a supported action claim and canonical input representation are fixed premises. The model is about durable lifecycle ordering, rather than recomputing policy qualification.

## Concrete records represented by abstract state

| Abstract concept | ECRC record | Ordinary record | Required interpretation |
|---|---|---|---|
| Raw request and terminal cancellation | `requests` | `requests` | Durable request identity/content. Reusing the same identity does not revive a cancelled request. |
| Full registered permit | `requests.permit_json` plus `issued_permits` | `requests.permit_json` plus `permit_registry` | An atomic issued action includes a bound reservation and registry entry. This is not yet dispatch authority. |
| Held/committed/released unit | `reservations`, `capacity_state` | `holds`, `budgets` | `reserved` corresponds to held and `spent` to committed. A committed unit is never replenished within this fixed key. |
| Durable intent | `delivery_outbox` | `delivery` | Contains the immutable permit key and payload. The row persists after reconciliation. |
| Service effect/dedup binding | Independent sink `effects` | Same independent sink | Persistent key-to-payload/effect mapping, separate from the client. |
| Locally completed receipt | `receipt_log`, `executions`, receipted outbox row | `receipts`, receipted delivery row | Completion changes the same held unit to committed in the same client transaction as the receipt. |
| Requests/ACKs in transit | Worker HTTP request and transport state | Same worker and transport | Volatile or external state, not a client ledger row. A request can outlive the worker that sent it. |

An abstract `Done` stage maps primarily to the receipted delivery record, not to a hypothetical `requests.state='done'`: concrete request rows may remain `issued`. If numeric S and C are derived from reservation sets, the model assumes the concrete counters accurately represent those sets; this is not an independent verification of SQL arithmetic. X must be derived from the persistent service effect history, not defined as C or as the number of receipts.

## Important implementation distinctions preserved by the abstraction

1. **Cancellation safety is a transactional held-unit property.** The ECRC wrapper's request cancellation check (E 139–140) is outside the inherited arm transaction. The inner held check (ED 60–65) prevents a grant if cleanup wins the writer lock and releases first. Ordinary arm does not directly read the `requests.cancelled` flag; it checks the registered held unit inside its transaction (OD 161–170). A common abstract guard `not cancelled` is acceptable only as a derived reachable-state condition alongside the actual held check and atomic cancellation, not as a claim that both source functions test the same flag.
2. **The low-level release API is not the S8 safe-release boundary.** L 797–845 changes a reserved unit to released without consulting delivery state. S8 cleanup's absence-of-intent guard is what makes pre-arm release safe. A model of the complete controlled path must not be presented as a guarantee for arbitrary direct calls to `ledger.release`.
3. **Durable arm and completion survive expiry.** Time checks apply to a new arm. A retry can recover the existing intent and finish it later. Removing or refusing such transitions would miss the recovery semantics being studied.
4. **There are three distinct durable commit points.** Client arm, sink effect commit and client reconciliation must be interleavable. Combining them into a distributed atomic step removes the unknown-outcome state and cannot support the intended contribution.
5. **The concrete worker normally skips sending a freshly read receipted job** (W 29–31), but stale worker copies and requests already in flight can still produce late matching POSTs. A model that permits Send for a retained completed intent is a conservative abstraction of stale copies; one that forbids new Send after completion must still permit existing in-flight requests to reach the sink.
6. **Admission at capacity is terminal for that decision.** A rejected full-budget action cannot automatically become admitted when another request later cancels. A new attempt with a new business decision identity is a different operation. Model waiting/admission semantics must not silently replace this behavior.

## Assumptions, omissions and claim limits

- One fixed key has a fixed finite quota. There is no policy replacement, cross-revision budget migration, federated ledger, second sink namespace, multi-route resource coupling or reusable-concurrency quota.
- Request/permit/reservation/operation identities may be represented by finite symbols, with fixed immutable payload tokens. This abstracts canonical JSON and hash collision resistance. Stable business identity is supplied; alias identities and malicious record modification are not prevented by this abstraction.
- Proposal/evidence qualification, source authenticity, timestamp parsing, floating-point threshold endpoints, arbitrary malformed input, and mixed-claim provisional release/fallback are not modeled. O1's semantic gates and all of O2's input/fallback behavior are therefore not verified. A no-action capacity branch does not add coverage of these omitted gates.
- Successful issuance is treated as atomic because both source wrappers use one SQLite write transaction. The checker does not prove database serializability, SQL implementation correctness, the ECRC containment wrapper under all Python exceptions, power-loss safety, corruption recovery, or operating-system/filesystem behavior.
- S8 also cancels received-but-unissued requests after 60 seconds (E 159–165; O 440–442). Unless explicitly added, that branch is outside this model. Do not identify permit expiry with that raw-request recovery lease.
- Expire should abstract supplied policy-time validity, not measured wall-clock commit time. Restricting the supplied clock to forward progress narrows the modeled call histories. Independent abstract expiry flags can overapproximate realizable expiry order, which is conservative for safety but should not be described as exact timestamp semantics.
- The service is trusted to create its synthetic effect and dedup binding atomically and to generate truthful ACKs. No bypass effect, forged ACK, lost durable dedup row, malicious client host or deletion/reset is included. X counts effects ever produced; in the baseline no deletion makes that equal to the durable sink-row cardinality.
- A finite message-domain/buffer abstraction, if used, must be declared. Collapsing duplicate identical messages can be justified only for the stated safety abstraction, not as a liveness or bounded-latency result. Request delivery and sink processing must remain possible independently of current client availability.
- Client failures may be represented as availability changes and loss of local transient knowledge; alternatively, failure between transactions can be stuttering. Neither representation establishes actual crash-recovery implementation coverage or power-loss durability. Without stated fairness and network-recovery assumptions there is no eventual-completion guarantee.
- Abstract states are global consistent execution states. Arbitrary sequential SQLite reads are not themselves a proof that a projected record bundle is one simultaneous state. Existing checkpoint projections can support a correspondence check, not a universal refinement proof.
- The two complete clients share this modeled contract. Passing does not establish an ECRC-exclusive mechanism, correctness advantage, runtime improvement or equality for every concrete history. It is a finite-model guarantee about the explicitly specified transition system and configurations.

## Model-review blockers before inclusion

The following specification differences would invalidate or materially weaken the proposed lifecycle claim and must be resolved or explicitly narrow the claim before model checking is presented as evidence:

1. `SinkCommit` reads `held`, `cancelled`, `expired`, client availability or remaining client budget. The source sink has no such access; adding these guards can hide the precise delayed-request counterexample.
2. The property to be checked, such as X ≤ S+C, is imposed as a state constraint, transition guard or reachability filter. The actual reservation admission guard S+C < L is legitimate source behavior; filtering globally unsafe states is not. Defining effects to equal receipts or committed units would similarly make the desired relation circular.
3. Arm, sink commit and reconciliation are fused; receipt creation is allowed before a durable sink result; or losing an ACK rolls back an effect. Each erases or changes a real source boundary.
4. Crash or timeout automatically destroys all possible in-flight requests, removes durable effect/dedup state, reclaims armed capacity, or makes the sink wait for client recovery. These are absent from the controlled source path.
5. Expiry/revocation automatically revokes an existing armed grant, or recovery checks fresh policy validity before returning an existing intent. This contradicts both adapters' branch order.
6. Full-capacity issuance is modeled as waiting and later successful reissuance while the result is described as covering all S8 issuance calls. It must instead include the stored non-action branch or explicitly omit such calls.
7. `CancelUnarmed` can race independently with the hold check of Arm, rather than sharing an atomic writer boundary; or the model grants cancellation safety through a flag without preserving the real held-unit check.
8. A transition called `UnknownArmedRetain` merely filters violating states instead of representing the absence of an authorized release transition. Retention is a concrete transition restriction, not an external invariant oracle.
9. O1–O6 are all advertised as verified despite fixed legal input, omitted claim fallback and abstract atomic commits. The scope must distinguish verified lifecycle properties from assumed input/transaction conditions.
10. Finite exploration is reported as code-level refinement, unbounded proof, liveness, real-effect exactly-once computation, or a comparative advantage. Neither this mapping nor the planned finite checker supports those conclusions.

A mutant allowing release of an armed unknown unit can be useful as an automatically generated boundary counterexample. It must be labeled a changed abstract specification, not an observed failure of either complete implementation. A baseline safety claim requires complete exploration of each declared finite instance with no violating-state filters and preserved checker output/configuration hashes.
